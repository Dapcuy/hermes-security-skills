# ADR-005: Validator Image Versioning (immutable Version + Digest)

## Status

Accepted.

## Konteks

Validator adalah bagian dari jalur pembuktian: hasil `validation-result.json` menjadi evidence yang dirujuk temuan. Bila image validator berubah diam-diam di belakang tag `latest`, dua eksekusi dengan task yang sama bisa menghasilkan perilaku berbeda tanpa jejak — evidence menjadi tidak bisa direproduksi, audit tidak bisa menjawab "kode apa yang berjalan saat itu", dan perbandingan hasil antar waktu tidak bermakna. Dalam konteks keamanan, image yang bisa berubah diam-diam juga vektor serangan: registry yang terkompromi atau tag yang di-retag bisa menyuntikkan kode ke jalur eksekusi tanpa terdeteksi. Yang dibutuhkan: identitas image yang immutable, tercatat di execution plan, dan bisa diverifikasi sebelum dijalankan.

## Keputusan

Validator image menggunakan **immutable/versioned image** — tidak ada `latest`:

```
hermes-validator-http:0.1.0
hermes-validator-http:0.1.1
hermes-validator-http:0.2.0
```

Execution plan **wajib menyimpan image version**, dan idealnya merujuk digest:

```
runtime:
  provider: docker
  image: hermes-validator-http@sha256:...
```

Aturan verifikasi:

- Docker adapter memverifikasi **signature + digest** image sebelum menjalankan (lihat fase 6): signature diverifikasi oleh adapter sebelum image dijalankan (mis. cosign/notation), trust store/publik key didokumentasikan dan didistribusikan bersama project.
- **Digest mismatch = reject** — bagian dari exit criteria fase Docker validator runtime.
- Sediakan jalur **build-from-source** dari repo untuk user yang tidak ingin menarik image dari registry; adapter menerima kedua path, verifikasi tetap wajib (digest dari build lokal tercatat di audit log).
- User tidak perlu melakukan `docker build` untuk penggunaan normal — image diproduksi pipeline CI (build -> scan -> SBOM -> sign -> publish ke OCI-compatible registry).

Tujuan yang dijadikan dasar keputusan: reproducibility, auditability, evidence provenance, dan deterministic validation.

## Konsekuensi

- Setiap evidence bisa menyebut dengan tepat image (version/digest) yang memproduksinya — provenance evidence menjadi dapat diverifikasi, bukan klaim.
- Audit historis mungkin: eksekusi lama tetap bisa direproduksi dengan image versi yang sama, meski versi terbaru sudah berbeda.
- Supply chain pada image registry tidak lagi berbasis percaya-butuh-verifikasi: meski registry terkompromi, image tanpa signature valid atau dengan digest yang berbeda ditolak adapter.
- Upgrade validator menjadi keputusan eksplisit: versi baru di-adopt lewat perubahan execution plan/registry, bukan efek samping pull diam-diam.
- Trade-off: pipeline rilis menjadi bagian wajib project (CI yang memproduksi image signed + SBOM), dan disiplin versi harus dijaga — setiap perubahan image wajib naik versi.
- Rollback mudah: kembali ke versi image sebelumnya adalah mengubah referensi di execution plan/registry.
