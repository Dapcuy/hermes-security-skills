# ADR-009: Credential Provider & Secret Handling

## Status

Accepted (diperkenalkan pada v2.0; komponen eksplisit di Phase 4 sebagai credential provider v0).

## Konteks

Pengujian IDOR/BOLA dan authenticated flow membutuhkan kredensial multi-account. Pola yang paling mudah — menaruh token di dalam skill, di dalam prompt, atau di dalam konteks reasoning — adalah pola yang paling berbahaya: kredensial bisa ikut terekam di memory, evidence, log, dan report; bisa bocor lewat prompt injection; dan bisa terbawa ke engagement berikutnya. Selain kredensial test account, project juga membutuhkan kredensial internal (control-channel token ke proxy, CA private key pada mode MITM). Bila kredensial internal ini dikelola manual, ia menjadi surface kebocoran dan beban operasional yang justru menggoda untuk "dipasang permanen". Prinsip arsitektural project sudah menyatakan: credentials never touch the reasoning context. Keputusan ini menjabarkan bagaimana prinsip itu diwujudkan secara mekanis.

## Keputusan

**Credential provider** ditambahkan sebagai komponen arsitekturnya sendiri (di luar reasoning path) dengan aturan:

1. **Penyimpanan terpisah**: credential disimpan di credential store terpisah — OS keychain bila tersedia, atau file yang di-exclude dari repo dan di-encrypt. Tidak pernah di dalam repo, memory files, knowledge, evidence, atau report. Credential store tidak ada di repo — lokasinya di luar.
2. **Reference-only untuk Hermes**: Hermes tidak pernah melihat nilai credential. Skill dan approval hanya merujuk reference:

```
accounts: [account-a, account-b]
```

3. **Injection oleh control plane saat eksekusi**:
   - Proxy provider: menyuntikkan header/cookie pada saat replay, di dalam hermes-proxy container.
   - Docker validator: credential di-mount sebagai input file di dalam container, tidak pernah muncul di stdout validator.
4. **Sanitasi otomatis**: setiap evidence, log, dan result discan terhadap credential yang aktif sebelum dipersist — sanitasi terjadi sebelum data menyentuh reasoning context.
5. **Lifecycle**: credential terikat pada authorization engagement; expired authorization berarti credential reference tidak lagi bisa dipakai; rotasi didorong setelah engagement selesai.

**Kredensial internal project** dikelola otomatis oleh control plane — bukan token eksternal yang diurus manual:

- **Control channel token**: ephemeral per-engagement, mengautentikasi control plane <-> hermes-proxy container; di-generate otomatis, mati bersama container, tidak pernah terlihat Hermes.
- **CA private key** (mode MITM, post-MVP): di-generate per-engagement, di-mount read-only ke proxy container, dihancurkan bersama engagement; tidak pernah persist di repo atau evidence.

Tidak ada token eksternal yang dikelola manual — keputusan ADR-002 menghapus kebutuhan tersebut.

## Konsekuensi

- Nilai kredensial tidak pernah berada di konteks LLM, sehingga kebocoran lewat prompt injection, memory dump reasoning, atau report tidak mungkin lewat jalur konteks.
- Skill yang membutuhkan test account cukup mendeklarasikan `requires_credentials: true` dan mereferensikan akun — portabel antar deployment karena nilainya tinggal di store masing-masing.
- Sanitasi otomatis membuat evidence dan report aman dibagikan ke program bug bounty tanpa risiko membocorkan kredensial test.
- Kredensial internal bersifat ephemeral: tidak ada rahasia jangka panjang yang layak dicuri dari deployment; kompromi satu engagement tidak membuka engagement lain.
- Trade-off: credential provider adalah komponen baru yang harus dibangun dan diuji (injection + sanitasi terverifikasi sebagai exit criteria Phase 4), dan skill yang butuh akun tidak bisa dijalankan penuh sebelum provider v0 tersedia.
- Binding ke authorization membuat kebocoran berdampak terbatas waktu: kredensial yang terekspos otomatis kehilangan keabsahan saat engagement berakhir.
