# ADR-004: Ephemeral Container Lifecycle

## Status

Accepted.

## Konteks

Container yang dibiarkan hidup setelah eksekusi adalah sumber masalah keamanan dan korektness: state yang tertinggal di dalam container bisa terbawa ke eksekusi berikutnya (menghasilkan "bukti" yang sebenarnya artefak sesi sebelumnya), container yang terlupakan memakan resource dan menyimpan data target di luar kendali retention, dan instance yang bisa "dipakai ulang" mengundang kontaminasi antar engagement. Model yang dipakai project mengharuskan setiap eksekusi berdiri sendiri: input dari execution plan yang disetujui policy, output evidence yang dinormalisasi, tanpa memori internal. Kebalikannya juga berlaku — membiarkan state persist di dalam container membuat container berperan sebagai memory, padahal persistent memory yang sah hanyalah evidence yang telah dinormalisasi dan case memory di luar container. Abort manual (kill switch) juga harus punya makna yang sama kuatnya dengan lifecycle normal: tidak ada gunanya menghentikan reasoning kalau container masih berjalan di belakang.

## Keputusan

Setiap execution bersifat **ephemeral** dengan lifecycle tetap:

```
Create -> Mount controlled input -> Apply policy -> Start
       -> Validate -> Collect result -> Collect artifacts -> Destroy
```

Workspace per eksekusi terstruktur dan terpisah:

```
jobs/
└── val-001/
    ├── input/      validation-task.json
    ├── output/     validation-result.json
    ├── artifacts/
    └── logs/
```

Aturan yang mengikat:

- Container **tidak menjadi persistent memory**. Evidence yang persistent hanyalah hasil yang telah dinormalisasi.
- Container yang berjalan saat **manual abort wajib di-kill dan dibersihkan oleh abort handler** — berlaku untuk validator maupun hermes-proxy.
- **Cleanup success rate adalah metrik wajib** yang diukur di benchmark (target: 100%).
- Lifecycle test wajib: create -> destroy tanpa container yang tertinggal — bagian dari exit criteria fase Docker.
- Pola yang sama berlaku untuk hermes-proxy: state tidak pernah persist di dalam proxy container; proxy dibuat, menjalankan tugas, mengumpulkan evidence, lalu di-destroy setiap eksekusi/engagement.

## Konsekuensi

- Tidak ada kontaminasi antar eksekusi: setiap run mulai dari keadaan bersih dengan input yang controlled, sehingga evidence mencerminkan eksekusi itu sendiri.
- Data target tidak menumpuk di container: retention policy (redact/hapus saat engagement berakhir) bekerja karena tidak ada state yang lolos di luar jobs/ dan memory/.
- Abort benar-benar menghentikan: kill switch menghentikan queue, revoke approval, dan menghapus container yang berjalan — tidak ada proses yatim yang terus mengirim traffic.
- Resource leak terkendali dan terukur: cleanup success rate menjadi metrik eksplisit, bukan asumsi.
- Trade-off: eksekusi menanggung biaya create/destroy per run (sedikit lebih lambat daripada instance panjang), dan abort handler harus andal — kegagalan cleanup harus terdeteksi dan dilaporkan, bukan diam-diam.
- Karena state tidak persist di container, semua yang berharga (result, artifacts, logs) harus dikumpulkan ke workspace SEBELUM destroy — urutan lifecycle tidak boleh dilanggar.
