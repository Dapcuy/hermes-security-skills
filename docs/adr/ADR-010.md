# ADR-010: Docker Network Mode — network=none pada MVP, Egress via Proxy sebagai Escalation

## Status

Accepted (diperjelas pada v2.0; direvisi pada v2.1 untuk menetapkan hermes-proxy sebagai satu-satunya komponen egress).

## Konteks

Validator dan container lain pada project ini mengeksekusi data yang berasal dari target — konten yang tidak bisa dipercaya. Bila container validator punya akses jaringan bebas, data target bisa menggerakkan container melakukan fetch ke URL manapun (termasuk out-of-scope, cloud metadata endpoint, atau infrastruktur penyerang), dan "validasi" berubah menjadi kanal exfiltrasi/SSRF yang tumbuh sendiri. Sebaliknya, beberapa operasi memang butuh jaringan (replay/mutation HTTP ke target). Solusi naif — membuka egress di semua container — melipatgandakan tempat yang harus di-audit dan membuat scope validation harus benar di banyak titik sekaligus. Selain itu, network mode yang tidak dieksplisitkan cenderung "membaik sendiri" menjadi unrestricted saat implementasi berjalan: asumsi egress masuk lewat fitur, bukan lewat keputusan.

## Keputusan

Network bersifat **deny-by-default**:

1. **MVP (Phase 5): `network: none` untuk validator** — satu-satunya mode yang didukung. Validator tidak melakukan fetch ke manapun; input validation diberikan sebagai file hasil replay (dari hermes-proxy atau dari user), dan validator hanya menganalisis data yang sudah ada. Test wajib: container yang mencoba akses jaringan harus gagal — ini bagian dari acceptance criteria.
2. **hermes-proxy adalah satu-satunya pengecualian** — satu-satunya container dengan privilege egress. Daripada membuka egress di banyak tempat, semua traffic keluar dikonsolidasikan di satu komponen yang policy-nya in-line (lihat ADR-002).
3. **Capability dengan `requires_network: true` hanya dapat dijalankan proxy provider.** Tidak ada provider lain yang boleh mengirim traffic ke target; provider yang tidak memenuhi syarat (mis. butuh network tapi berjalan network=none) wajib menolak dengan error eksplisit.
4. **Post-MVP escalation yang eksplisit**: validator yang butuh egress di-route melalui hermes-proxy container (Validator -> hermes-proxy -> destination), dengan destination diizinkan berdasarkan execution plan yang sudah disetujui policy, dan redirect di-re-validate terhadap scope.
5. **Tidak pernah `network_mode: host`.**
6. Validator dengan `requires_network: true` baru dapat didaftarkan di validator registry setelah egress proxy tersedia (post-MVP).

Pola arsitektur:

```
Validator (network=none)    -- mode default: tanpa jaringan sama sekali
Validator (egress, post-MVP) -> hermes-proxy (policy in-line) -> allowed destination only
```

## Konsekuensi

- Attack surface jaringan terkonsolidasi: scope validation, redirect handling, dan rate limiting hanya perlu benar di satu tempat (proxy), bukan di setiap container.
- Validator tidak bisa dimanipulasi konten target menjadi kanal egress — fetch out-of-scope dari validator secara teknis tidak mungkin, bukan hanya dilarang.
- Replay aktif dan analisis data terpisah tegas: validator menganalisis hasil yang sudah terekam, proxy yang berinteraksi dengan target — pemisahan ini juga menyederhanakan audit.
- Escalation ke egress validator bersifat eksplisit dan tertib: harus lewat jalur proxy, tidak bisa "diaktifkan cepat" dengan opsi Docker.
- Trade-off: validator yang idealnya fetch langsung (mis. analisis yang butuh respons live) harus menunggu post-MVP atau menerima data hasil replay — keterbatasan fungsional yang disengaja demi keamanan pada MVP.
- Acceptance test network (container yang mencoba akses jaringan harus gagal) menjadi bagian permanen dari CI/runtime tests, bukan pengujian sekali saja.
- Konfigurasi deployment tetap harus memenuhi prasyarat ADR-007: Hermes sendiri tidak boleh punya akses network langsung di luar jalur control plane.
