# ADR-001: Capability Abstraction

## Status

Accepted (sejak versi awal roadmap; tetap berlaku pada v2.1).

## Konteks

Skill pada project ini menjelaskan metodologi keamanan, sedangkan operasi nyata (replay HTTP, validasi berbasis Docker, analisis lokal) dilakukan oleh implementasi konkret. Jika skill menulis operasi itu secara langsung — misalnya "jalankan replay dengan tool X" atau "jalankan validasi di Docker" — maka setiap perubahan implementasi memaksa perubahan di puluhan skill sekaligus. Hal ini sudah terbukti terjadi: pergantian Caido menjadi hermes-proxy pada v2.1 akan menjadi perubahan yang menghancurkan bila skill mencantumkan nama tool secara hardcoded. Selain itu, control plane tidak bisa mengevaluasi policy secara konsisten bila operasi dinyatakan dalam bahasa tool — policy perlu tahu *apa* yang diminta (risiko, kebutuhan network, kebutuhan approval), bukan *nama program* yang akan dijalankan. Tanpa lapisan abstraksi, juga sulit membedakan operasi read-only dari operasi yang mengirim traffic ke target — perbedaan yang menentukan komponen mana yang boleh mengeksekusinya.

## Keputusan

Setiap operasi yang diperlukan skill dinyatakan sebagai **capability** — operasi abstrak dengan semantik, risk level, dan requirement yang terdaftar di capability registry. Skill hanya menyatakan kebutuhan:

```
requires:
  - request_replay
  - response_comparison
```

Skill tidak boleh meng-hardcode tool (`gunakan mitmproxy`, `gunakan curl`, `gunakan Docker`). Provider yang mengeksekusi capability ditentukan oleh capability registry, bukan oleh skill maupun Hermes. Registry mencatat per capability: risk level, `default_provider`, `requires_scope`, `requires_network`, `requires_approval`. Contoh mapping pada registry:

```
inspect_request     -> proxy   (read-only, dari event store)
request_replay      -> proxy   (satu-satunya jalur replay, requires_network)
json_diff           -> local   (komputasi murni, tanpa side effect)
openapi_analysis    -> docker-openapi
```

Tidak ada fallback otomatis antar provider: provider utama unavailable berarti capability gagal dengan error eksplisit (fail-closed), dan policy denial berarti stop — bukan degradasi diam-diam. Provider `local` dibatasi ketat untuk operasi komputasi murni tanpa network dan tanpa side effect; capability yang butuh jaringan aktif hanya boleh dijalankan oleh proxy provider.

## Konsekuensi

- Provider dapat berganti (hal ini nyata: Caido -> hermes-proxy pada v2.1) tanpa mengubah satu baris skill; yang berubah hanya registry dan provider implementation.
- Skill-linter memvalidasi bahwa tidak ada hardcode tool di dalam `skills/` dan bahwa setiap capability yang dirujuk valid terhadap registry — pelanggaran menggagalkan CI.
- Control plane bisa mengevaluasi policy sebelum eksekusi karena kebutuhan operasi terdaftar secara terstruktur (risk, network, scope, approval), bukan ditebak dari nama tool.
- Penambahan provider baru (mis. provider Docker, provider lokal, provider masa depan) tidak memerlukan perubahan skill; fundamental architecture tetap stabil.
- Harga yang dibayar: ada satu lapisan indirection lagi — capability, provider, dan registry harus didesain, didokumentasikan, dan dijaga konsisten; nama capability menjadi contract yang tidak boleh berubah semaunya.
- Operasi read-only (history/inspect) boleh dilayani provider lain karena tidak mengirim traffic ke target; batas ini harus dijaga agar "read-only" tidak menjadi celah egress.
