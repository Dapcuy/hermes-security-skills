# ADR-012: Web/API Scope Boundary

## Status

Accepted (diperkenalkan pada v3.0 — ROADMAP §2; fokus project dipersempit dan dinyatakan eksplisit).

## Konteks

Arsitektur project (skill + capability + policy + controlled runtime) pada prinsipnya netral domain: dengan menambah skill, capability, dan tool image, scope bisa melebar ke wireless, mobile, binary analysis, firmware, infrastruktur cloud, dan seterusnya. Tanpa boundary yang dinyatakan eksplisit, tiga masalah muncul. Pertama, ruang lingkup yang melebar membuat investasi tipis: metodologi web/API yang dalam jauh lebih bernilai daripada metodologi sepuluh domain yang dangkal. Kedua, setiap domain tambahan membawa surface keamanan dan supply-chain baru (tool image, validator, payload) yang harus di-review dengan standar yang sama (ADR-011) — memperluas domain = memperluas TCB secara efektif. Ketiga, kontributor dan pengguna tidak punya dasar keputusan yang objektif untuk menolak/menerima kontribusi di luar domain inti, sehingga keputusan scope selalu kasus-per-kasus dan rawan scope creep. Scope boundary perlu menjadi keputusan arsitektural yang tertulis, bukan asumsi.

## Keputusan

Fokus project adalah **Web/API security** — satu domain, dalam.

- **In-scope** (ROADMAP §2.1): web security, API security, HTTP security, authentication/authorization, business logic, injection, webhooks, SSRF, file upload, CORS, CSRF, GraphQL, JWT, OAuth/OIDC analysis, multi-tenant isolation, rate limiting, security misconfiguration, HTTP traffic analysis, controlled vulnerability validation, security reporting.
- **Out-of-scope** (ROADMAP §2.2): wireless, Bluetooth, RF, physical security, malware development, persistence, lateral movement, credential stuffing, password cracking, destructive testing, data exfiltration, automatic disclosure/submission, unrestricted mass scanning.
- **Ditunda (deferred), bukan ditolak selamanya**: wireless security, mobile security, binary analysis, firmware analysis. Keempatnya butuh tool, runtime, dan metodologi yang berbeda secara fundamental; dibuka hanya sebagai **future scope** dengan keputusan owner + ADR tambahan.
- Tool/metodologi di luar Web/API hanya dapat dipertimbangkan bila memiliki kebutuhan nyata terhadap project dan disetujui sebagai future scope — tidak diadopsi lewat jalur kontribusi biasa.
- **Discovery/recon tetap in-scope** sepanjang melayani metodologi web/API: passive recon, subdomain enumeration, port scanning (connect scan), technology fingerprinting/probing, dan attack-surface prioritization adalah bagian dari Web/API methodology (tier `discovery/`), bukan domain terpisah.
- Capability registry dan Tool Registry tetap generik secara mekanisme (provider/risk/approval per entri), sehingga pembukaan scope di masa depan tidak mengubah arsitektur — hanya menambah entri yang melewati review.

## Konsekuensi

- **Empat skill deferred**: `cloud-security`, `mobile-security`, `binary-analysis`, `firmware-analysis` tidak dikembangkan pada v3.0 dan dikecualikan dari routing/linter sebagai deferred (nama tetap terdaftar agar tidak dianggap skill hilang).
- Kontribusi di luar domain dapat ditolak dengan rujukan ke ADR ini — keputusan scope tidak lagi subjektif per PR.
- Kedalaman > keluasan: budget skill/tool/validator dikonsolidasikan ke web/API (termasuk HTTP methodology dan business-logic analysis), yang diharapkan meningkatkan kualitas reasoning dan menurunkan false positive pada domain inti.
- Discovery tetap membutuhkan guardrail ketat (approval per tool, budget, stop conditions) karena aktif — tetapi tetap satu keluarga metodologi dengan web/API, bukan pembukaan domain baru.
- Risiko "arsitektur terkunci": boundary ini bukan permanen — membuka domain baru cukup dengan keputusan owner + ADR baru + entri registry yang lolos review; tidak ada perubahan fundamental yang diperlukan.
