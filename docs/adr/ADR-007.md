# ADR-007: Enforcement & Integration Contract — Control Plane sebagai MCP Server

## Status

Accepted (diperkenalkan pada v2.0).

## Konteks

Pada desain awal, guardrail direpresentasikan sebagai instruksi markdown yang diharapkan diikuti model. Ini memiliki kelemahan fundamental: kepatuhan bergantung pada disiplin model, sehingga guardrail semacam itu tidak bisa disebut security boundary — model bisa terganggu prompt injection, bisa salah prioritas, atau sekadar lupa menjalankan check. Sementara itu, kebutuhan nyata project adalah menguji target nyata atas izin, dan itu hanya sah jika ada mekanisme yang secara teknis tidak bisa dilewati. Masalah integrasinya juga nyata: kalau policy check adalah CLI terpisah yang "harus dipanggil Hermes dengan rajin", maka keandalan enforcement bergantung pada kepatuhan yang sama yang mau dihilangkan. Terakhir, enforcement hanya valid bila deployment-nya benar — Hermes yang diberi docker CLI, shell bebas, atau akses network langsung bisa mem-bypass seluruh control plane tanpa memecahkan satupun mekanismenya.

## Keputusan

Model enforcement didefinisikan eksplisit dalam **dua mode**:

```
Mode ADVISORY (Phase 1 - 3):
  guardrail berupa markdown instruction; kepatuhan
  bergantung disiplin model; TIDAK security boundary;
  hanya untuk development, reasoning dry-run, lab lokal.

Mode ENFORCED (Phase 4 ke atas):
  guardrail dieksekusi di tool path; Hermes secara
  teknis TIDAK BISA mem-bypass karena satu-satunya
  jalan ke provider adalah melalui control plane.
  Ini barulah security boundary.
```

Konsekuensi yang diterima eksplisit: sebelum Phase 4 semua operasi pasif/advisory dan tidak ada active testing terhadap target nyata; klaim "policy" dalam dokumentasi hanya berlaku penuh setelah Phase 4.

Integration contract: control plane di-expose ke Hermes sebagai **MCP server**, bukan CLI opsional:

```
hermes-security serve --mcp     # untuk Hermes (tool path)
hermes-security list-skills     # untuk manusia & CI
hermes-security check-policy    # untuk manusia & CI
```

Aturan integration:

- Hermes hanya melihat MCP tool yang sudah melalui **allowlist**.
- Setiap tool berisiko mengeksekusi policy check **sebelum** provider dipanggil — di dalam proses yang sama.
- Tidak ada operasi yang "meminta Hermes rajin menjalankan check-policy" — check berjalan karena tidak ada jalur lain.
- Policy files dan capability registry **read-only** dari sudut pandang Hermes.

Prasyarat deployment (syarat penggunaan, didokumentasikan di README):

```
Hermes TIDAK diberi: docker CLI / docker socket;
  shell atau network tool bebas (curl, ncat, dsb.);
  akses network langsung / koneksi langsung ke proxy container;
  write access ke policy/, capabilities/, runtimes/.

Hermes HANYA diberi: control-plane MCP tools;
  read-only access ke skills/, knowledge/, templates/.
```

Jika Hermes di-deploy dengan akses penuh, seluruh model enforcement batal. Adapter multi-agent (fase 13) hanya mendukung client yang bisa menjamin restricted tool access.

## Konsekuensi

- Keandalan guardrail berhenti bergantung pada kepatuhan model: policy dieksekusi di tool path karena arsitektur, bukan karena instruksi.
- Permitasiran jelas: di Phase 1–3 project hanya boleh dipakai untuk reasoning dan lab; klaim keamanan berlaku penuh hanya setelah enforcement aktif.
- MCP server mode menjadi satu-satunya integration path yang didukung untuk operasi berisiko — CLI tetap ada untuk manusia dan CI, bukan untuk Hermes.
- Prasyarat deployment menjadi bagian dari kontrak produk: penggunaan di luar prasyarat menghanguskan jaminan, dan itu harus dinyatakan di README, bukan disimpan di catatan internal.
- Trade-off: control plane Go kini berada di jalur setiap operasi dan menjadi trusted computing base — kompromi control plane = kompromi seluruh isolation, sehingga ia di-review lebih ketat dan tidak pernah menerima instruksi dari konten target.
- Tool allowlist menambah langkah rilis: setiap tool baru yang di-expose ke Hermes harus melewati review, bukan sekadar ditambahkan.
