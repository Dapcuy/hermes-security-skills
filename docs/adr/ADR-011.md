# ADR-011: Tool Supply-Chain Architecture

## Status

Accepted (diperkenalkan pada v3.0 — ROADMAP §35–§42; memformalkan prinsip tool image yang sudah berlaku sejak v2.1 menjadi arsitektur supply-chain utuh).

## Konteks

Project ini menggunakan third-party security tools (nuclei, ffuf, subfinder, httpx, nmap, dan sejenisnya) sebagai bagian dari capability `endpoint_discovery` dan `template_based_validation`. Tool-tool tersebut secara desain adalah kode pihak ketiga yang: tidak ditulis/direview penuh oleh project, berkemampuan melakukan network access aktif, menerima input yang sebagian berasal dari target (untrusted), dan membawa dependensi konfigurasinya sendiri (mis. nuclei templates — supply chain di dalam supply chain). Repository katalog seperti `hackingtool` menawarkan ratusan tool siap pakai — mengadopsinya sebagai toolbox menempatkan dependency tidak terpercaya langsung di jalur eksekusi yang punya egress. Tanpa arsitektur supply-chain eksplisit, sebuah tool = jalur eksekusi arbitrer di dalam lingkungan engagement: bisa exfiltrate, bisa memodifikasi evidence, bisa mem-bypass budget. Karena itu relasi terhadap third-party tool harus menjadi keputusan arsitektural, bukan praktik ad-hoc per tool.

## Keputusan

Prinsip dasar:

```
Tool = untrusted dependency
Capability = trusted interface
```

Mekanisme:

1. **Tool Registry** (`tools/registry.yaml`): satu-satunya sumber kebenaran identitas tool — name, category, image, version, digest, signature requirement, risk, provider, capability mapping, network requirement, approval requirement, evidence parser. Tool yang tidak terdaftar tidak bisa dieksekusi.
2. **Dedicated image per tool**: satu tool = satu image (`hermes-tool-nuclei`, `hermes-tool-ffuf`); tidak ada image gabungan. Install saat build (CI), bukan saat runtime — runtime container read-only, non-root, tanpa kemampuan install.
3. **Wrapper fail-closed**: third-party tool tidak pernah dijalankan langsung. Wrapper memverifikasi policy bundle + execution plan, memaksa budget + rate limit, menjalankan tool, menormalisasi output menjadi evidence berprovenance (versi tool, versi template/aset, image digest).
4. **Templates/wordlists baked & pinned**: konfigurasi tool adalah supply chain tersendiri. Nuclei templates dan wordlists (mis. SecLists) di-pin per versi/commit, di-bake ke image saat build, diverifikasi sebelum dipakai; runtime TIDAK PERNAH auto-update konfigurasi tool.
5. **Digest + signature verification**: image di-pin `@sha256:...` di registry; Docker adapter memverifikasi digest dan signature sebelum menjalankan; mismatch/unsigned = reject (fail-closed).
6. **Approval per tool di registry**: risk dan persyaratan approval ditentukan per tool di Tool Registry — bukan di level capability. Contoh: `endpoint_discovery` lewat nmap mewajibkan approval `always`; lewat subfinder pasif cukup conditional.
7. **Katalog kandidat, bukan dependency**: repository katalog (mis. `hackingtool`) hanya dipakai sebagai candidate discovery. Pipeline adopsi: relevance filter → Web/API scope → security review → license review → supply-chain review → version pinning → dedicated image → SBOM → security scan → image signing → Tool Registry. Tidak ada tool yang otomatis masuk hanya karena ada di katalog.

## Konsekuensi

- Menambah tool baru = proses supply-chain lengkap, bukan satu baris konfigurasi — biaya adopsi sengaja dibuat terlihat. Kecepatan bertumbuh melalui pipeline yang bisa diulang, bukan lewat pintu pintas.
- Attack surface third-party tool tetap ada, tetapi berjalan di dalam container dengan privilege minimum (baseline §31: read_only, cap_drop ALL, network terkontrol) sehingga dampak kompromi tool terbatas pada budget/scope yang sudah di-approve.
- Output tool bukan final authority: hasil "vulnerable" tetap observation yang masuk finding lifecycle + false-positive analysis (tool tidak pernah menentukan finding).
- Pinning templates/wordlists berarti deteksi bisa tertinggal dari ancaman terbaru — pembaruan dilakukan sebagai perubahan versi ter-review di registry, bukan auto-update runtime; trade-off keamanan vs mutlak-update dipilih ke arah keamanan.
- Verifikasi signature hanya sekuat trust root-nya — public key/trust store didistribusikan bersama project dan dijaga out-of-band.
- Tool Registry sendiri menjadi aset keamanan: perubahannya ter-audit dan di-review, karena melonggarkan entri registry = melonggarkan approval per tool.
