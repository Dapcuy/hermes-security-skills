# ADR-003: Docker Validator Runtime

## Status

Accepted.

## Konteks

Validasi hipotesis keamanan membutuhkan eksekusi kode (parser, komparator, analisis OpenAPI) yang tidak boleh berjalan bebas di host dan tidak boleh menjadi "shell bebas" untuk Hermes. Menjalankan validator langsung di host berarti menggabungkan lingkungan reasoning dengan lingkungan eksekusi — hasil dan efek sampingnya tidak bisa diisolasi, dan host OS ikut memengaruhi perilaku validator. Mengizinkan Hermes memanggil `docker run` secara arbitrary juga bukan solusi: itu hanya memindahkan shell bebas ke bentuk lain. Yang dibutuhkan adalah runtime yang controlled, ephemeral, dan reproducible — dengan resource limit, network policy, dan mounts yang dikendalikan control plane, bukan oleh Hermes. Selain itu, hasil validator harus identik antar mesin dan antar waktu agar evidence punya makna; itu hanya bisa dicapai kalau eksekusi berjalan di image yang tetap dan kontrak input/output yang eksplisit.

## Keputusan

Docker digunakan sebagai **controlled, ephemeral, reproducible validation runtime**. Docker bukan: unrestricted shell untuk Hermes; autonomous pentest environment; tempat semua security tools dikumpulkan; atau security boundary satu-satunya.

Arsitektur:

```
Hermes -> Policy -> Execution Plan -> Docker Runtime
       -> Curated Validator Image -> Validator -> Structured Result
```

Karakteristik runtime:

- **Curated images, bukan satu image besar**: `hermes-validator-http`, `hermes-validator-openapi`, `hermes-validator-json`, `hermes-validator-python` — masing-masing dengan tujuan sempit dan dependency minimum. Tidak ada `hermes-security-all-tools`.
- **Security baseline** tiap container: `read_only: true`, `cap_drop: ALL`, `no-new-privileges:true`, `pids_limit: 64`, `mem_limit: 512m`, `cpus: 1.0`, non-root user, timeout, controlled mounts, controlled network, no host filesystem access, no Docker socket. `privileged`, `network_mode: host`, docker.sock mount, dan unrestricted network dilarang.
- **Execution contract**: validator menerima `validation-task.json` dan menghasilkan `validation-result.json`; validator menghasilkan *observation*, bukan keputusan final — Hermes yang menafsirkan.
- **Runtime adapter Go** memegang semua tanggung jawab operasional (availability, image verification signature + digest, creation, limits, network policy, mounts, timeout, execution, result collection, cleanup, audit). Hermes meminta `DockerRuntime.Execute(ExecutionPlan)`, bukan menjalankan `docker run` bebas.
- **Validator registry** memetakan validator -> provider/image/version/risk/requires_network; capability memilih validator melalui registry.
- Lintasan platform: Linux, Windows (Docker Desktop/WSL2), dan macOS (Docker Desktop); validator wajib menghasilkan behavior/interface yang sama di semua platform, host path di-abstraction menjadi `/workspace/input|output|artifacts`. Timeout dikalibrasi terhadap platform terlama (bind mount Windows).

## Konsekuensi

- Eksekusi validator konsisten dan reproducible: input dan image yang sama menghasilkan perilaku yang sama di Linux, Windows, dan macOS — syarat bagi evidence yang bisa dipercaya.
- Kontrol penuh ada di control plane (Go), yang menjadi trusted computing base; karena itu control plane harus di-review dengan standar lebih ketat dan tidak pernah menerima instruksi dari konten target.
- Hermes tidak pernah menyentuh Docker; satu-satunya antarmuka adalah execution plan yang sudah lolos policy.
- Menjalankan validator dengan `network: none` (lihat ADR-010) berarti validator hanya menganalisis data yang sudah ada — replay aktif tetap urusan hermes-proxy, bukan validator.
- Trade-off: user membutuhkan Docker yang terinstal (WSL2 di Windows didokumentasikan sebagai prasyarat), dan pipeline distribusi image (build, scan, SBOM, sign, publish — fase 6) menjadi bagian wajib dari project.
- Determinism turun kelas bila tool pihak ketiga masuk; karena itu tool eksternal hanya boleh sebagai image terpisah dengan wrapper + provenance (lihat ROADMAP §13.1 dan RULES.md).
