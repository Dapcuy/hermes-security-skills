# ADR-002: Self-Hosted Proxy Provider (hermes-proxy) Menggantikan Caido MCP

## Status

Accepted (revisi v2.1 — menggantikan keputusan sebelumnya yang memakai Caido melalui Caido MCP).

## Konteks

Versi awal desain mengandalkan tool proxy pihak ketiga (Caido) yang diakses melalui MCP. Keputusan itu membawa beban struktural yang tidak bisa diselesaikan dengan konfigurasi: operasi HTTP tergantung pada produk eksternal dengan siklus rilis sendiri, jembatan MCP menambah lapisan yang tidak dikontrol project, dan model membutuhkan token eksternal yang dikelola manual — token Caido dan OAuth flow menjadi surface kebocoran tersendiri dan kehilangan sifat ephemeral yang dibutuhkan model keamanan. Yang paling serius: policy tidak bisa dijamin in-line. Evaluasi policy di control plane sementara eksekusi terjadi di tool pihak ketiga menciptakan celah TOCTOU — request bisa berubah antara "disetujui" dan "dikirim". Project butuh komponen proxy yang sepenuhnya berada di bawah pipeline keamanan yang sama dengan validator: curated, versioned, signed, ephemeral, dan policy-nya dievaluasi di tempat yang sama dengan tempat eksekusi.

## Keputusan

Project membangun **hermes-proxy** — interception proxy self-hosted yang berjalan sebagai **ephemeral Docker container** dengan pola yang sama persis dengan validator image: curated, versioned, signed. Caido dan Caido MCP dihapus total; tidak ada jembatan pihak ketiga untuk operasi HTTP dan tidak ada token eksternal yang dikelola manual.

Prinsip desain:

1. **Docker-first**: proxy berjalan sebagai ephemeral container — create -> mount policy bundle -> run -> collect evidence -> destroy. State tidak pernah persist di dalam container.
2. **Policy in-line**: policy bundle di-mount read-only (hash-verified); setiap request dievaluasi di dalam proxy sebelum dikirim. Check dan eksekusi berada di jalur yang sama, bukan "policy di control plane, eksekusi di tempat lain".
3. **TOCTOU guard**: request di-re-validate saat eksekusi di dalam proxy, bukan hanya saat planning di control plane.
4. **Fail-closed**: policy bundle tidak valid atau tidak ter-mount berarti proxy menolak semua operasi.

Komunikasi control plane <-> proxy memakai **control channel internal**: token ephemeral per-engagement yang di-generate otomatis oleh control plane, tidak pernah terlihat oleh Hermes, mati bersama container, dan channel hanya listen di Docker network internal. Pengembangan bertahap: Mode 1 (MVP) adalah replay/mutation/compare engine tanpa TLS MITM dan tanpa intercept browser; Mode 2 (post-MVP) menambahkan full interception + capture traffic browser dengan CA certificate per-engagement.

Hermes tidak pernah punya akses network langsung — satu-satunya jalur HTTP adalah melalui proxy. Redirect default NO-FOLLOW; setiap redirect yang diikuti di-re-validate terhadap scope, dan respons dari origin out-of-scope tidak boleh masuk reasoning sebagai konten.

## Konsekuensi

- Semua operasi HTTP aktif (replay, mutation, comparison) hanya dieksekusi di dalam proxy container; capability read-only (history/inspect) boleh dilayani control plane dari event store tanpa menyentuh target.
- Proxy menjadi satu-satunya komponen dengan privilege egress — attack surface jaringan project terkonsolidasi di satu choke point yang policy-nya in-line (lihat ADR-010).
- Tidak ada lagi token eksternal: pemilik deployment tidak perlu mengelola kredensial pihak ketiga, dan kredensial internal bersifat ephemeral sehingga kebocoran jangka panjang tidak mungkin.
- Trade-off biaya: project kini memelihara engine HTTP sendiri (Go, dependency version-pinned + supply-chain review, dikemas lewat CI) — ini kerja tambahan yang disengaja demi kontrol penuh atas jalur eksekusi.
- Interception penuh (TLS MITM + browser capture) ditunda ke post-MVP; sampai saat itu kemampuan proxy dibatasi replay/mutation/compare — pendekatan bertahap mencegah kompleksitas MITM membebani validasi MVP.
- Event store dan evidence reference proxy harus didesain agar hasil read-only bisa dilayani tanpa eksekusi aktif, menjaga pemisahan baca vs kirim traffic.
